# parallel-docker-workers

A dockerised variant of `parallel-dispatch`: each worker agent runs inside its own container with full in-container freedom, while the host coordinator still owns plan distribution, gate approvals, and PR opening.

## Context
_Codebase facts and constraints learned during grilling._
- Current parallel dispatch lives in `skills/parallel-dispatch.md`. Unit of work is one whole feature; each agent gets a temporary git worktree via `isolation: "worktree"` on the `Agent` tool; concurrency cap is 3; per-feature gates are surfaced individually as background completions land; a combined-diff `code-reviewer` pass runs after all PRs are opened (advisory only).
- Developer agents (e.g. `agents/go-developer.md:78-86`, `agents/ios-developer.md:37-43`) run their own self-review loop with `code-reviewer` (up to 3 cycles, must reach APPROVE) before returning. Coordinator does not invoke `code-reviewer` separately in serial mode.

## Decisions
_Resolved through grilling. Each entry references the question that produced it._
1. **Unit of work per container** — one whole feature, mirroring the existing `parallel-dispatch` granularity. Container receives the task file (`tasks/<slug>.md`), runs the developer agent end-to-end (all slices + self-review loop), returns the branch. Slice-level fan-out (b) was rejected because slice ordering kills the theoretical parallelism; single-tool sandboxing (c) was rejected as a different problem (sandbox helper, not worker agent).
2. **In-container process** — `claude` CLI invoked with `--print` and `--dangerously-skip-permissions`. The container's blast-radius boundary makes skipping permissions safe; the existing agent + skill ecosystem and any nested `Agent` tool calls work without re-implementation. Agent SDK (b) and custom HTTP wrapper (c) were rejected — neither solves a problem we have, and both add work.
3. **Auth inside the container** — long-lived Claude Code OAuth token (e.g. `CLAUDE_CODE_OAUTH_TOKEN`, exact env var to confirm at implementation) passed via `docker run -e`. The host minted the token once via `claude setup-token`. Mounting `~/.claude` (b) was rejected as it leaks the entire credential store to a `--dangerously-skip-permissions` worker; raw `ANTHROPIC_API_KEY` (c) was rejected because it requires a separate billing path the user doesn't currently use.
4. **Filesystem / repo model** — host coordinator creates a git worktree (`git worktree add ../wt-<slug> -b feature/<slug>`) and bind-mounts it at `/workspace` in the container. Container writes commits into the mounted worktree; host sees them on the same branch and is the only party with `git push` credentials. Container clone-inside (b) was rejected because it doubles the secrets surface (git push creds in-container); whole-repo mount (c) was rejected as it breaks isolation. Implementation note: pass `--user $(id -u):$(id -g)` on Linux to avoid root-owned host files; macOS Docker Desktop is unaffected.
5. **Result return and parallelism mechanism** — coordinator fires one `Bash` call per feature with `run_in_background: true`, each invoking `docker run --rm ... <image> /entrypoint.sh`. The entrypoint runs `claude --print` and, before exiting, writes a structured `.worker-result.json` (status: `APPROVE|BLOCKED`, branch, commits[], summary, blockers[]) into the bind-mounted worktree. When `docker run` returns, Bash notifies the coordinator, which reads the result file and surfaces the gate. Stdout-only return (b) was rejected as brittle text parsing; long-lived worker pool with queue (c) was deferred as out of scope.
6. **Coordinator integration** — ship as a new sibling skill `skills/parallel-docker-dispatch.md`. The existing `skills/parallel-dispatch.md` (worktree-based) remains the default; Docker dispatch is opt-in for work that needs system-level freedom. Replacing parallel-dispatch outright (b) was deferred. Single skill with an internal mode flag (c) was rejected as the auth/image/result divergence is too large to share one prose flow.
7. **Image strategy** — one generic image (`claude-worker:latest`) with `claude` CLI + git + node + python + go + build-essential pre-baked. Worker can `apt install` more at runtime. Per-language images (b) was rejected as it forces routing logic into the dispatch skill and N Dockerfiles to maintain. Minimal base + on-demand install (c) was rejected for slow/non-deterministic dispatch.
8. **Network policy** — open network (default Docker bridge), worker can reach the public internet and the host's LAN. Aligns with "full access inside the container". Egress allowlist (b) was rejected as a maintenance treadmill; HTTP proxy (c) was rejected as solving a hostile-actor threat model that doesn't match coordinator-trusted agents. Note: open network includes the host's LAN; user is on notice if private services are LAN-bound.
9. **Container timeout and cleanup** — hard wall-clock timeout (default 30 min per feature, configurable per dispatch) enforced via `timeout 1800 docker run --rm ...`. On timeout, host kills the container and synthesises a `BLOCKED` result with reason `timeout`. `--rm` always — container disposable, worktree retains everything needed for post-mortem. Keep-on-failure (b) was rejected as low-value debugging gain for an ongoing cleanup cost; no timeout (c) was rejected as one stuck container would stall the whole dispatch.
10. **Concurrency cap and resource limits** — match `parallel-dispatch`'s cap of 3, with no per-container CPU/memory limits initially. Cap reasoning is gate cognitive load (each gate needs user attention), not host resources, so it transfers identically. Explicit limits (b) deferred until actual contention observed. Different cap (c) rejected to keep symmetric reasoning with the existing skill.
11. **Trigger / routing** — coordinator routes to `parallel-docker-dispatch` when the user's dispatch instruction explicitly says "in containers" / "with docker" / "dockerised" (or close variant). No silent mode switch. Per-feature flag in the task file (b) was rejected as it leaks operational concerns into stack-agnostic plans and makes mixed batches awkward. Heuristic auto-routing (c) was rejected — misclassification would be infuriating and the "does this need full system access" call is exactly the judgment the user should make.
12. **Verification / canary** — ship a `tasks/_canary.md` fixture (trivial: create `CANARY.txt` with today's date, commit) plus a small host-side test script that dispatches it through the skill and asserts: branch exists, commit landed, `.worker-result.json` is `APPROVE`, container is gone, worktree is cleanable. Used during initial wiring debug and as a regression smoke test when the image, entrypoint, or skill prose changes. Test-on-first-real-feature (b) and no-check (c) were rejected — too costly an iteration loop and silently regression-prone respectively.

## Slices

### Slice 1 — Worker image builds and `claude` is callable inside it
**Outcome:** Running `docker run --rm claude-worker:latest claude --version` on the host prints a Claude Code version string.
**Test (Red):** Host-side script `scripts/test-image.sh` runs `docker build -t claude-worker:latest docker/` then `docker run --rm claude-worker:latest claude --version` and asserts the output matches `claude code, version *`. File: `scripts/test-image.sh`.
**Implementation (Green):** `docker/Dockerfile` based on a slim Debian/Ubuntu base with `claude` CLI installed (via official install method or npm), plus `git`, `node`, `python3`, `go`, `build-essential`, and `ca-certificates`. Files: `docker/Dockerfile`.
**Refactor:** none expected.
**Acceptance:** `scripts/test-image.sh` exits 0 from a clean checkout.

### Slice 2 — Entrypoint runs the worker prompt and writes `.worker-result.json`
**Outcome:** Given a bind-mounted worktree containing `tasks/<slug>.md` and an OAuth token in env, the container produces `/workspace/.worker-result.json` with the agreed schema and exits 0.
**Test (Red):** `scripts/test-entrypoint.sh` creates a temp dir with a stub `tasks/_smoke.md` ("respond APPROVE, do nothing else"), runs the image with that dir mounted at `/workspace` and `CLAUDE_CODE_OAUTH_TOKEN` from env, and asserts that `.worker-result.json` exists with required fields (`status`, `branch`, `commits`, `summary`, `blockers`) and `status == "APPROVE"`. File: `scripts/test-entrypoint.sh`.
**Implementation (Green):** `docker/entrypoint.sh` that reads `/workspace/tasks/<slug>.md` via env-supplied slug, invokes `claude --print --dangerously-skip-permissions` with a system prompt instructing the agent to perform the work and print a final JSON object matching the result schema, then writes that JSON to `/workspace/.worker-result.json`. Files: `docker/entrypoint.sh`, `docker/Dockerfile` (ADD/CMD).
**Refactor:** factor the result-schema into a single shell variable or doc comment so the skill prose can reference it.
**Acceptance:** `scripts/test-entrypoint.sh` exits 0 and the file matches schema.

### Slice 3 — Single-feature dispatch wrapper drives one container end-to-end
**Outcome:** `scripts/dispatch-docker-worker.sh <slug>` creates a worktree on `feature/<slug>`, runs one container with the right mounts/env/timeout, and on success leaves a committed worktree plus a valid `.worker-result.json`.
**Test (Red):** `scripts/test-dispatch-single.sh` invokes the wrapper against the canary fixture (`tasks/_canary.md`, written in this slice) and asserts: worktree at `../wt-_canary` exists, branch `feature/_canary` has at least one commit ahead of base, `CANARY.txt` exists in the worktree with today's date, `.worker-result.json` shows `APPROVE`, container has been cleaned up (`docker ps -a` shows no `claude-worker-_canary*`). File: `scripts/test-dispatch-single.sh`.
**Implementation (Green):** `scripts/dispatch-docker-worker.sh` that creates the worktree, computes the bind mount path, invokes `timeout 1800 docker run --rm --user $(id -u):$(id -g) -v <wt>:/workspace -e CLAUDE_CODE_OAUTH_TOKEN -e SLUG=<slug> claude-worker:latest /entrypoint.sh`, and on timeout synthesises a `BLOCKED` result. Files: `scripts/dispatch-docker-worker.sh`, `tasks/_canary.md`.
**Refactor:** extract worktree-create and worktree-teardown helpers if the wrapper grows past one screen.
**Acceptance:** `scripts/test-dispatch-single.sh` exits 0, including a clean teardown of the worktree afterwards (`git worktree remove ../wt-_canary`).

### Slice 4 — Skill `parallel-docker-dispatch.md` exists and is indexed
**Outcome:** Coordinator can find the new skill via `skills/README.md` and `SYSTEM_PROMPT.md`; the skill prose covers all 12 decisions and the trigger phrasing.
**Test (Red):** `scripts/test-skill-indexed.sh` greps `skills/README.md`, `SYSTEM_PROMPT.md`, and `agents/README.md` (if relevant) for the string `parallel-docker-dispatch` and asserts each grep succeeds; also greps the new skill file for each of: `Trigger`, `Concurrency cap`, `OAuth`, `worktree`, `30 min`, `_canary` to confirm decision coverage. File: `scripts/test-skill-indexed.sh`.
**Implementation (Green):** Write `skills/parallel-docker-dispatch.md` mirroring `skills/parallel-dispatch.md`'s structure (When to invoke / Fan-out shape / Per-feature gate / Combined-diff pass / Forbidden actions), substituting Docker-specific mechanics. Add one-line entry to `skills/README.md`. Add Skill-index row to `SYSTEM_PROMPT.md`. Files: `skills/parallel-docker-dispatch.md`, `skills/README.md`, `SYSTEM_PROMPT.md`.
**Refactor:** if the new skill duplicates large blocks of `parallel-dispatch.md`, replace duplication with a "see parallel-dispatch.md for shared semantics" cross-reference rather than copy-paste.
**Acceptance:** `scripts/test-skill-indexed.sh` exits 0; manual read of the skill confirms all 12 decisions are reflected.

### Slice 5 — Multi-feature parallel dispatch (cap of 3) with per-feature gates
**Outcome:** Dispatching ≥2 canary copies in one user instruction produces N concurrent containers (capped at 3), each surfaces its own gate as it completes, and a queued surplus releases on each gate clear.
**Test (Red):** `scripts/test-dispatch-parallel.sh` writes `tasks/_canary_a.md`, `_canary_b.md`, `_canary_c.md`, `_canary_d.md` (four copies of the canary, distinct file names so commits diverge), invokes the dispatch wrapper in a fan-out shell (4 backgrounded `dispatch-docker-worker.sh` calls with a semaphore of 3), and asserts: at any moment `docker ps` shows ≤3 `claude-worker` containers; eventually all 4 worktrees exist with their commit; all 4 result files are `APPROVE`. File: `scripts/test-dispatch-parallel.sh`.
**Implementation (Green):** Update `scripts/dispatch-docker-worker.sh` to be safe to invoke concurrently (unique container names per slug, no shared temp paths). Document the fan-out + cap-of-3 semaphore semantics in `skills/parallel-docker-dispatch.md` so the coordinator knows to enforce it via backgrounded Bash calls and queueing logic. Files: `scripts/dispatch-docker-worker.sh`, `skills/parallel-docker-dispatch.md`.
**Refactor:** if the canary fixtures multiply, factor a `tasks/_canary_template.md` plus a tiny generator.
**Acceptance:** `scripts/test-dispatch-parallel.sh` exits 0; max-concurrency observation matches cap.

### Slice 6 — Coordinator routing recognises the trigger phrase
**Outcome:** `SYSTEM_PROMPT.md` and the user-facing `~/.claude/CLAUDE.md` describe when to invoke `parallel-docker-dispatch` vs `parallel-dispatch`, in language the coordinator can act on.
**Test (Red):** `scripts/test-routing-prose.sh` greps `SYSTEM_PROMPT.md` for an unambiguous routing rule (e.g. a sentence containing both "in containers" and `parallel-docker-dispatch`), and confirms the existing `parallel-dispatch` description was edited to clarify it is the worktree-based default. File: `scripts/test-routing-prose.sh`.
**Implementation (Green):** Edit Step 2 of `SYSTEM_PROMPT.md` to add a "Docker-dispatch trigger" sub-bullet alongside the existing "Parallel-dispatch trigger", citing the trigger phrases. Manually copy `SYSTEM_PROMPT.md` to `~/.claude/CLAUDE.md` per the project's stated workflow (the `sync-upstream` skill does not touch the user-global file). Files: `SYSTEM_PROMPT.md`.
**Refactor:** none expected.
**Acceptance:** `scripts/test-routing-prose.sh` exits 0; manual smoke: in a fresh session, asking the coordinator to "dispatch features X and Y in containers" is correctly routed.

## Deferred (out of scope)
| Item | Why deferred | Related decision |
|------|--------------|------------------|
| Long-lived worker pool with task queue | Different product than feature-scoped containers; only worth building if there's a 24/7 worker need we don't currently have | Decision 5 |
| Replace `parallel-dispatch.md` entirely with the Docker variant | Worktree dispatch has zero infra cost and remains the right default for most parallel work; revisit only if Docker dispatch becomes universally preferred | Decision 6 |

## Open Questions
- **Exact env var name for the OAuth token** — Decision 3 names `CLAUDE_CODE_OAUTH_TOKEN` as the working assumption. Confirm against current `claude` CLI docs at implementation time; if the CLI uses a different variable, update Slice 2 and the dispatch wrapper.
- **Image hosting** — initial assumption is local `docker build` only (single-dev-machine setup, no registry push). If a second machine ever needs to dispatch, add a registry push step. Not blocking.
- **MCP server isolation** — the host's `claude` config may include MCP servers (Gmail, Calendar, Drive). The in-container `claude --print` runs without `~/.claude` mounted (per Decision 3), so it should not see those MCP servers, but the entrypoint should explicitly start with a clean config dir to be safe. Verify during Slice 2.
- **Combined-diff `code-reviewer` pass** — assumed mechanically identical to `parallel-dispatch` (branches still on the host post-dispatch, so the pass runs on the host the same way). Confirm during Slice 4 skill-prose drafting; if subtleties surface, add a Decision row.
- **Token rotation mid-dispatch** — if the OAuth token expires while a long-running container is mid-flight, the worker fails. Out of scope for this skill; reasonable mitigation is to mint a fresh token before any large parallel run.
