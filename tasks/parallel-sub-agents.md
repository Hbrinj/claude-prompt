# parallel-sub-agents

Define how the coordinator dispatches multiple developer sub-agents in parallel and how the workflow accounts for concurrent in-flight features.

## Context
_Codebase facts and constraints learned during grilling._
- This repo (`claude-prompt`) is the agent/skills library — work here edits markdown prompts in `agents/`, `skills/`, plus `CLAUDE.md` workflow rules. No executable code.
- The coordinator workflow today (per `~/.claude/CLAUDE.md`) is single-feature, end-to-end: one `feature/<name>` branch, one plan in `tasks/<slug>.md`, one developer agent dispatched, one PR.
- Each feature already has its own isolation surface: branch, plan file, checkpoint at `features/<name>.checkpoint.md`, and one row in `features/all_features.md`. PRs handle merge conflicts via the normal git/GitHub flow.
- Reference repo `/Users/geekair/development/domain-mem` was assessed for fit:
  - Single Go package; files form a strict sequential dependency chain (errors → core → CLI wiring). Workstream/track-level parallelism within one feature is **infeasible** there — no frontend/backend seam, no module boundary, slices share files.
  - Feature-level parallelism is **already operational** — `tasks/`, `features/`, and `.ddmem/coordinator-and-agents.md` encode it. Concurrent `feature/<slug>` branches share only the ledger row in `features/all_features.md`, which the coordinator serialises after each merge.

## Decisions
_Resolved through grilling. Each entry references the question that produced it._
1. **Granularity = feature-level (option d)** — the parallelizable unit is a whole feature. Coordinator dispatches multiple `feature/<name>` branches concurrently, each running its own end-to-end Step 2 (plan → branch → developer agent → review loop → PR). Slice-level (a) and workstream-level (b) parallelism are rejected: slice-level fights TDD discipline (slices share files); workstream-level requires a structural seam (frontend/backend, module split) that target repos like `domain-mem` don't have. Feature-level reuses the existing isolation boundary (branch/plan/checkpoint/PR) instead of inventing a new one.
2. **Trigger = user-explicit list (option a)** — coordinator only runs parallel dispatch when the user names the features to dispatch. No automatic pull from `TODO.md` (those items are pre-triage and need their own `/grill-plan` session each). Keeps the human gate on *what* gets parallelised; the throughput win is purely on the dispatch side.
3. **Parallelism scope = Step 2 only (option a)** — Step 1 grilling stays serial per feature; all N plans must be written and approved by the user before any implementation begins. Coordinator then dispatches N developer agents in parallel for Step 2. Rationale: Step 1 is interactive with one user — concurrent grilling would thrash; Step 2 is long-running and non-interactive, which is where the wall-clock win actually exists.
4. **Dispatch mechanism = single message, multiple `Agent` calls with `run_in_background: true` (option b)** — coordinator fans out N developer-agent calls in one tool-use turn; each completion lands as a notification, allowing the coordinator to surface per-feature review gates in completion order rather than waiting on the slowest. Foreground (a) was rejected because it gives the user no signal during the longest phase of work; sequential background (c) burns extra dispatch turns for no benefit.
5. **Working-directory isolation = `isolation: "worktree"` on every parallel `Agent` call (option a)** — the Agent tool's purpose-built primitive: each call gets its own temporary git worktree, returns `{path, branch}` on completion, auto-cleans if no changes were made. Each developer agent's existing protocol (create `feature/<name>`, commit per slice, push) runs unchanged inside the worktree. Manual `git worktree add` (b) was rejected as reinventing what (a) automates; no-isolation (c) contradicts Decision 4.
6. **Per-feature review gate in completion order (option a)** — each feature surfaces its own *"Implementation is complete. Approve to open the PR"* gate the moment its developer agent + code-reviewer loop finishes; user approves it; PR opens for that feature; siblings keep running. Failure isolation falls out automatically — if any one feature stalls (e.g. code-reviewer exhausts 3 cycles), only that gate is blocked; siblings continue. Batched-at-end (b) was rejected because it couples N features to the slowest, wasting the throughput parallelism is paid for.
7. **Conflict handling between concurrent PRs = standard GitHub merge flow (option a)** — coordinator opens each PR independently; if two features touched overlapping files, the second-to-merge resolves the conflict via the normal git/GitHub flow, with the user making the call. No coordinator-side conflict detection or sequential rebase loop. Rationale: by Decision 2 the user already picked the feature list — picking non-overlapping features is their call. Pre-dispatch overlap detection (b) was deferred as a possible future enhancement (see Deferred).
8. **Documentation split (option c)** — `~/.claude/CLAUDE.md` gets a short Step 2 branch that names the trigger condition (multiple features in user list → parallel dispatch) and points to the new skill file; full mechanics (worktree handling, fan-out template, per-feature gate ordering, completion tracking) live in `skills/parallel-dispatch.md`. Mirrors the existing `grill-plan` precedent — substantive mechanics live in `skills/`, CLAUDE.md references them by name. (a) inline-everything would bloat the always-loaded playbook; (b) skill-only would hide the trigger from the playbook the coordinator reads every session.
9. **Per-feature execution = developer agent self-reviews (option c)** — every developer agent (`agents/go-developer.md`, `agents/android-developer.md`, etc.) gets a mandatory section instructing it, after coding, to invoke `code-reviewer`, address all CRITICAL+MAJOR findings, repeat ≤3 cycles, then push the branch and return. Coordinator's per-feature responsibilities collapse to: fan-out, per-feature gate, PR open. Industry consensus across Anthropic's multi-agent research system, Claude Code subagents docs, Cursor 2.0/3.2 background agents, OpenHands, Aider, and LangGraph supervisor pattern: each worker owns its inner loop end-to-end; coordinators that narrate sub-agent internals (CrewAI hierarchical mode) measurably under-perform. (a) introduces a new wrapper agent type for no behavioural gain over (c); (b) — coordinator runs N inner state machines — is exactly the failure mode the literature flags (chatty orchestrator, token blowup, fragile prose-state). One implication: in serial mode the developer agent self-reviews, replacing today's coordinator-driven review loop — single protocol for both paths, no behavioural divergence.
10. **Concurrency cap = 3 parallel features per dispatch (default, configurable in `skills/parallel-dispatch.md`)** — bounds the cognitive surface the coordinator tracks at any moment, the merge-conflict surface across in-flight PRs, and the token cost of fan-out. Aligns with Anthropic's research-system 3–5 sub-agent range (Cursor's cap of 8 is for fully-isolated independent tasks; our features may share files, so a smaller cap is safer). If the user names more than 3 features, coordinator dispatches the first 3 and queues the rest, releasing each new dispatch as a slot frees on per-feature gate approval.
11. **Combined-diff reviewer pass after all parallel PRs open** — once every feature in a parallel batch has its PR opened, coordinator runs `code-reviewer` once over the union of branch diffs vs `main` (e.g. `git diff main...feature-X main...feature-Y main...feature-Z`), surfaces the verdict to the user before any merges. Catches cross-feature interactions invisible to per-PR review (overlapping types, contradictory edits to the same prose, double-defined sections). Aider and ainativedev coding-agent guides flag this as the single highest-leverage reliability move when fan-out tasks share any state. The pass is advisory — it does not block merges; the user decides what to do with findings.
12. **Resume semantics = per-feature resume only (option a)** — no batch manifest. After interruption, the user resumes one feature at a time using the existing protocol (`features/<name>.checkpoint.md` per feature). To resurrect the still-running subset of a batch, the user re-issues the parallel dispatch with the remaining feature names. Avoids a second source of truth (batch manifest) that could drift from per-feature checkpoints; smallest possible extension to the existing single-feature resume rule.

### 1. Create `skills/parallel-dispatch.md`
Author the new skill file with full mechanics. Sections to include: when triggered (user names ≥2 features in one dispatch), pre-dispatch validation (each feature has an approved plan in `tasks/<slug>.md`, no `feature/<name>` branch already exists), the fan-out template (single message with N `Agent` calls, each with `subagent_type: <stack>-developer`, `isolation: "worktree"`, `run_in_background: true`, the brief is `tasks/<slug>.md`), concurrency cap of 3 (queue the rest, release as gates approve), per-feature gate ordering (handle in completion order, surface *"Implementation complete for <slug> — approve to open PR"* prompt the moment each lands), failure isolation rule (siblings continue regardless of one feature's failure), combined-diff reviewer pass (after all PRs open, run `code-reviewer` over the union of branch diffs vs `main`, surface findings, advisory not blocking), resume rule (per-feature checkpoint resume; re-issue parallel dispatch for remaining features), and forbidden actions (NEVER dispatch parallel without approved plans for all named features; NEVER skip the per-feature gate; NEVER auto-merge without user approval; NEVER include the same feature in two concurrent dispatches).
